# Updating exported game data

Everything under `static/data` is generated by the D2R Multi-Export tool: `keyed/`,
`strings/`, `sprites/`, `extras/` and `manifest.json`. The manifest lists every other file
with its byte size and SHA-256. Never edit these files by hand; export again instead.

The website has no installation step of its own. It serves and imports the files in
`static/data` exactly as the exporter writes them.

## Workflow

1. Stop `pnpm dev`, because Windows cannot rename a directory that a file watcher holds open.
2. Run the exporter with this checkout as its website target, either with `--website` or the
   desktop client's **Website Repository** setting. Keep `--out` outside `static/data`:

   ```powershell
   dotnet run --project .\D2RMultiExport.Console -- export `
     --mod-data "..\d2r-reimagined-mod" --casc-data "<path-to-CascView-extraction>" `
     --out ".\test-output" --website "..\d2r-reimagined-website"
   ```

3. Commit the `static/data` changes on their own, separate from code changes.

The exporter owns validating and installing the data. It only replaces `static/data` after a
successful, complete export, and it refuses without changing anything if `static/data` holds
files its current manifest does not list. For the details, see the exporter's `README.md`
("Website update") and `docs/WEBSITE-INTEGRATION.md`. Its working directories
`static/.data.install-*`, `static/.data.backup-*` and `static/.data.failed-*` sit beside
`static/data`, and `.gitignore` excludes them.

## Retired migration scripts

`data:restore-removed` and `data:remap-recipes` were removed. They patched earlier exports made
from incomplete source submissions, and the merged source export supersedes them. Every cube
recipe now ships a stable exporter `Id`. `src/lib/data/cube-recipe-aliases.json` stays as frozen
compatibility data, so links saved with old recipe numbers still resolve through
`src/lib/cube-recipe-ids.ts`. Do not edit exported recipe JSON or recipe identities to keep
links working.
