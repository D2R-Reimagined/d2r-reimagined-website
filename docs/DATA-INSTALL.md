# Installing exported game data

Everything under `static/data` is generated by the D2R Multi-Export tool: `keyed/`,
`strings/`, `sprites/`, `extras/` and `manifest.json`. The manifest lists every other file
with its byte size and SHA-256. Never edit these files by hand; install a new export instead.

`pnpm data:install` copies a bundle staged by the exporter into `static/data`. It works only
on the local checkout. It does not commit, push, publish or deploy anything.

## Workflow

1. Run the exporter against the intended mod source.
2. Stage the result with the exporter. The staging directory must be new or empty:

   ```powershell
   dotnet run --project .\D2RMultiExport.Console -- publish `
     --from .\test-output --staging C:\temp\d2r-stage
   ```

3. Preview, then install, from the website checkout. Stop `pnpm dev` first, because Windows
   cannot rename a directory that a file watcher holds open:

   ```powershell
   pnpm data:install --from C:\temp\d2r-stage --dry-run
   pnpm data:install --from C:\temp\d2r-stage
   ```

4. Check the installed contents against their manifest:

   ```powershell
   pnpm data:install --verify
   ```

5. Run the website checks:

   ```powershell
   pnpm test
   pnpm run check
   pnpm run build
   ```

6. Review `git status` and `git diff --stat -- static/data`, then commit the generated-data
   changes on their own, separate from code changes.

`--to <directory>` points any of these commands at a directory other than `static/data`,
for example a scratch copy.

## What the installer checks

Before it touches the destination, the staged bundle must pass all of these checks:

- `manifest.json` is a regular file with `SchemaVersion: 2`, `Succeeded: true`,
  `Complete: true`, and every step `Written`.
- Every `Files[]` path is a plain root-relative `/` path. Absolute paths, drive prefixes,
  backslashes, `.`/`..` segments, empty segments, characters or trailing dots and spaces that
  Windows rejects, reserved device names (`con`, `lpt1`, …) and the manifest itself are rejected.
- No two paths are equal, differ only in case, or use one listed file as another's directory.
- Every listed file exists under exactly that name, with the declared size and hash.
- The bundle contains nothing else: no unlisted files, empty directories, symbolic links or
  junctions. Links are never followed.
- The bundle and the destination do not contain each other.

It does not repeat any source or calculation validation; that is the exporter's job.

The destination must be missing, or contain only files its current `manifest.json` lists. A
hand-added file, an unreadable manifest or a link is reported and nothing is changed. Move or
delete such entries yourself, then run the installer again. The installer never deletes a
file it cannot identify as earlier generated output.

## Incomplete or unexpected bundles

Do not install a bundle that fails these checks. Fix the export and stage it again.

- `Succeeded: false` or a failed step means the export recorded errors.
- `Complete: false` means optional outputs were skipped. That includes bundles staged with the
  exporter's `--allow-incomplete`. The website always requires complete data, so this
  installer has no override.
- A missing, changed or extra file means the staging directory is not the bundle that
  `publish --staging` wrote. Do not copy files in or out by hand; stage again into an empty
  directory.

## How replacement works

1. The bundle's files and its exact manifest bytes are copied into a sibling directory
   `static/.data.install-<stamp>`. That copy is then verified. JSON is copied byte for byte
   and never parsed or rewritten.
2. `static/data` is renamed to `static/.data.backup-<stamp>`, and the verified copy is renamed
   to `static/data`.
3. The new `static/data` is verified again, and the backup is deleted.

Files missing from the new manifest, such as stale sprites or JSON, disappear because the whole
directory is replaced. If the new bundle matches the installed one exactly, nothing is changed.

If a rename or the final verification fails, the installer moves the backup back into place
and reports the result. The two renames are separate operations, not one atomic transaction.
If the process is killed between them, `static/data` may be missing and the previous data stays
in `static/.data.backup-<stamp>`. The next run refuses to start while a backup exists. Rename
the backup to `static/data`, or delete it, then run again. Leftover `.data.install-*`
directories hold only copies and can be deleted. `.gitignore` excludes all of these
directories.

## Retired migration scripts

`data:restore-removed` and `data:remap-recipes` were removed. They patched earlier exports made
from incomplete source submissions, and the merged source export supersedes them. Every cube
recipe now ships a stable exporter `Id`. `src/lib/data/cube-recipe-aliases.json` stays as frozen
compatibility data, so links saved with old recipe numbers still resolve through
`src/lib/cube-recipe-ids.ts`. Do not edit exported recipe JSON or recipe identities to keep
links working.
